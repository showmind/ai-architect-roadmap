组合优于继承
Composition Over Inheritance

通过对象组合而非类继承来达到代码复用，避免继承的脆性基类问题。

点击展开详情 →

一句话解释

使用对象组合而非类继承来实现代码复用，继承会创建脆弱的基类耦合，组合则提供灵活的运行时行为切换。

代码反例 / 正例

❌ 反例：继承脆性
class Bird {
  fly() { /* 拍翅膀 */ }
}
class Penguin extends Bird {
  // 企鹅不会飞，但继承了fly()
  // 必须覆盖或抛出异常
}
✅ 正例：组合灵活
interface FlyBehavior {
  void fly();
}
class Bird {
  FlyBehavior fly;
  void setFly(FlyBehavior f) {
    this.fly = f;
  }
}
new Bird().setFly(new NoFly());
// 运行时动态切换行为

实际架构场景

🏗️ 框架设计：Spring Framework 不让 Service 继承 BaseService，而是通过依赖注入组合各种 Strategy。运行时可以替换数据源的实现（MySQL → PostgreSQL），无需修改任何继承链。

面试考点

❓ 组合优于继承的优缺点是什么？
💡 优点：运行时灵活、松耦合、避免菱形继承问题。缺点：需要更多对象创建、代码量略增。核心在于"继承是静态的，组合是动态的"。
❓ 何时该用继承？
💡 当存在真正的"is-a"关系且子类不需要改变父类行为时。

高内聚低耦合
High Cohesion Low Coupling

模块内部紧密相关，模块之间松散依赖。这是衡量软件架构质量的黄金标准。

点击展开详情 →

一句话解释

每个模块内部元素紧密相关（高内聚），模块之间依赖最小化（低耦合），使系统易于维护和演进。

代码反例 / 正例

❌ 反例：低内聚高耦合
class OrderService {
  void validate() {}
  void saveToDB() {}
  void sendEmail() {}
  void generatePDF() {}
  void callPaymentAPI() {}
  // 一个类什么都做，修改一处影响全部
}
✅ 正例：高内聚低耦合
class OrderValidator { void validate() {} }
class OrderRepository { void save() {} }
class EmailNotifier { void send() {} }
class PDFGenerator { void generate() {} }
class PaymentGateway { void charge() {} }
// 每个类专注一件事，独立变化

实际架构场景

🏢 微服务拆分：电商系统拆分为订单服务、库存服务、支付服务。各服务独立部署、独立扩展（高内聚），通过 API Gateway 通信（低耦合）。订单服务升级不影响支付服务。

面试考点

❓ 如何判断模块是否"高内聚"？
💡 内聚度从低到高：偶然内聚 < 逻辑内聚 < 时间内聚 < 过程内聚 < 通信内聚 < 顺序内聚 < 功能内聚。理想是功能内聚——模块只做一件事。
❓ 耦合有哪些级别？
💡 内容耦合 > 公共耦合 > 外部耦合 > 控制耦合 > 标记耦合 > 数据耦合。目标是数据耦合。

接口隔离
Interface Segregation Principle

客户端不应依赖它不需要的接口。将庞大接口拆分为多个专用小接口。

点击展开详情 →

一句话解释

一个类对另一个类的依赖应该建立在最小的接口上——不要强迫客户端依赖它不使用的方法。

代码反例 / 正例

❌ 反例：胖接口
interface Worker {
  void work();
  void eat();
  void sleep();
}
class Robot implements Worker {
  void work() {}
  void eat() { throw new UnsupportedOperationException(); }
  void sleep() { throw new UnsupportedOperationException(); }
}
// 机器人被迫实现不需要的方法
✅ 正例：瘦接口
interface Workable { void work(); }
interface Eatable { void eat(); }
interface Sleepable { void sleep(); }
class Human implements Workable, Eatable, Sleepable {}
class Robot implements Workable {}
// 每个类只实现需要的接口

实际架构场景

🔌 USB 协议：USB-A、USB-C、Thunderbolt 是不同的接口规范，设备只实现需要的接口。打印机不需要音频接口，手机不需要视频输出接口。接口隔离让系统灵活适配。

面试考点

❓ ISP 和单一职责原则（SRP）有什么区别？
💡 SRP 关注类/模块的职责数量（一个类只有一个变更原因），ISP 关注接口的粒度（客户端不应被迫依赖不使用的方法）。ISP 是 SRP 在接口层面的体现。

DRY 原则深化
Don't Repeat Yourself — Evolved

DRY 不仅是代码复用，更是从代码复用→架构复用→平台复用的逐层升华。

点击展开详情 →

一句话解释

DRY 的本质是"每一块知识都有单一权威的表述方式"，从代码级别的函数复用，上升到架构级别的模式复用，最终到平台级别的能力复用。

代码反例 / 正例

❌ 反例：伪DRY
// 三个方法只是参数不同，本质是重复
void processOrder(Order o) { /* ... */ }
void processRefund(Refund r) { /* 类似逻辑 */ }
void processReturn(Return ret) { /* 类似逻辑 */ }
// "三处几乎相同的代码"仍是DRY违规
✅ 正例：真正的DRY演进
// 代码复用：提取公共函数
void process(Transaction t) { ... }

// 架构复用：使用模板方法模式
abstract class TransactionPipeline {
  abstract void validate();
  abstract void execute();
  final void process() { validate(); execute(); }
}

// 平台复用：构建交易服务平台
// 业务方只配置规则，平台处理所有基础设施

实际架构场景

🏗️ 复用三层：第一层——函数库（工具类）；第二层——架构框架（Spring 的 IoC 容器，所有项目复用同一套依赖管理）；第三层——平台（PaaS 平台提供部署、监控、日志，业务方只需写业务代码）。越往上复用级别越高，影响力越大。

面试考点

❓ DRY 和 KISS 有冲突吗？
💡 表面上看 DRY 鼓励抽象复用（可能增加复杂度），KISS 要求简单。平衡点在于：抽象的收益（减少重复）是否大于其维护成本。好的抽象是"简单且可复用"的。
❓ 什么是 AHA 编程（Avoid Hand-Abstraction）？
💡 当你发现第三次重复时才提取抽象，而非第一次。过早抽象是 YAGNI 违反者的借口，但过晚抽象是 DRY 违反者的借口。

模块化设计模式
Modular Design Patterns

微内核、插件化、分层架构——三种主流模块化模式，应对不同复杂度的系统需求。

点击展开详情 →

一句话解释

将系统组织为独立模块的架构模式：微内核（核心+扩展）、插件化（动态加载）、分层架构（单向依赖），各有适用场景。

代码反例 / 正例

❌ 反例：无模式的大泥球
// 所有模块混在一起
// 无法独立测试、部署、替换
// 修改一个功能可能影响所有其他功能
✅ 正例：分层架构
// 表现层 → 业务层 → 数据层
class PresentationLayer {
  void handleRequest() {
    bizLayer.process();
  }
}
class BusinessLayer {
  void process() {
    repo.save();
  }
}
// 依赖只能向内层传递

实际架构场景

🔧 VS Code：典型的插件化架构。核心编辑器是微内核，扩展（插件）是插件化模式，文件管理/调试/版本控制是分层架构。三个模式在同一产品中共存，各司其职。

面试考点

❓ 微内核和插件化的区别？
💡 微内核强调核心稳定+扩展灵活（如 Eclipse），插件化强调运行时动态加载/卸载（如 VS Code 扩展）。微内核是结构模式，插件化是部署模式。
❓ 分层架构的缺点？
💡 瀑布式依赖可能导致"过度设计"——简单需求也要穿越多层。好的做法是允许旁路（如 CQRS 允许读模型直接访问查询层）。
