HashMap · 哈希表

缓存设计 / 索引结构 / Redis Hash 底层
平均 O(1) · 最坏 O(n) ▼

核心思想

通过哈希函数 hash(key) % capacity 把任意键映射到数组下标，实现「以空间换时间」的接近常数级读写。当多个键映射到同一位置时产生「哈希冲突」，常用链地址法（数组 + 链表/红黑树）解决。Java 8 中链表长度超过 8 且数组容量 ≥ 64 时转为红黑树，退化最坏复杂度从 O(n) 改善为 O(log n)。

时间复杂度

  • 查询 / 插入 / 删除（平均）：O(1)
  • 查询 / 插入 / 删除（哈希冲突严重、退化为链表）：O(n)（转树后 O(log n)）
  • 扩容 rehash：O(n)（一次性摊还到每次操作为 O(1)）

实际系统中的应用

本地缓存Redis Hash 底层数据库索引（哈希索引）对象池 / 连接池

  • Redis Hash：底层为压缩列表（ziplist，小数据）/ 哈希表（dict）。一个 Hash 由两张哈希表（ht[0]、ht[1]）组成，用于渐进式 rehash。
  • Guava Cache / Caffeine：本地缓存核心就是 ConcurrentHashMap。
  • MySQL 自适应哈希索引：InnoDB 在内存中对热点页构建自适应哈希索引加速等值查询。

面试考点

为什么容量是 2 的幂扩容与 rehash负载因子 0.75哈希冲突解决

  • 容量取 2 的幂，可用 hash & (n-1) 代替取模，位运算更快。
  • 负载因子 0.75：空间与冲突概率的折中；超过则扩容为 2 倍并 rehash。
  • 为什么 String 适合做 key？其 hashCode 被缓存，重写过 equals 与 hashCode。

跳表 · Skip List

Redis ZSet 底层 / LevelDB · RocksDB
查找 O(log n) ▼

核心思想

在有序链表之上「加多层索引」——越往上节点越稀疏。查找时从最高层开始向右，遇更大值就下降一层，像「坐电梯 + 走楼梯」一样快速逼近目标，把链表的 O(n) 查找优化到 O(log n)。新节点层数由随机化（如 25% 概率上升一层）决定，保证结构平衡，无需像平衡树那样旋转。

时间复杂度

  • 查找 / 插入 / 删除：O(log n)（平均，期望意义下）
  • 空间：O(n)（额外索引约占 1.33n 个节点）

实际系统中的应用

Redis ZSetLevelDB MemTableRocksDBHBase 块索引

  • Redis ZSet：当元素数 > 128 或成员较大时，底层由跳表 + 字典组成。字典以 O(1) 按 member 查 score，跳表按 score 排序支持范围/排名查询，两者通过指针共享成员与分值。
  • LevelDB / RocksDB：内存中的 MemTable 用跳表实现，写入即有序，便于刷盘后做归并。

面试考点

为何不用红黑树随机层数范围查询优势

  • 相比平衡树，跳表实现简单、并发写冲突少，且天然支持高效范围扫描（树需中序遍历）。
  • Redis 为什么用跳表而不是红黑树做 ZSet？—— 范围查询（ZRANGE）跳表更优，且实现更简单。

B+ 树

MySQL InnoDB 索引结构
查找 O(log n) ▼

核心思想

一种多路平衡查找树，每个节点存放多个 key 与指针，树高很低（千万级数据通常仅 3~4 层）。B+ 树所有数据都挂在叶子节点，且叶子节点用双向链表串起，非叶子节点只存索引 key，因此范围查询和全表扫描极其高效，且每次查询都走同样深度的路径——稳定。

时间复杂度

  • 等值 / 范围查询：O(log n)（n 为数据量，实际高度极小）
  • 范围扫描：O(log n + m)（m 为结果条数，叶子链表顺序遍历）

实际系统中的应用

MySQL InnoDB 聚簇索引二级索引文件系统（NTFS/ext4）

  • 聚簇索引（主键）：InnoDB 的 B+ 树叶子节点直接存整行数据；因此「主键查询最快」「二级索引回表需再查主键树」。
  • 为什么用 B+ 树而非二叉树 / Hash：磁盘按页（16KB）读写，B+ 树「矮胖」减少磁盘 IO 次数；Hash 不支持范围查询，二叉树树太高。
  • 一个 3 层 B+ 树（阶数约 1200）可索引约 1200^3 ≈ 17 亿 行，仅需 3 次磁盘 IO。

面试考点

B+ 树 vs B 树聚簇 vs 二级索引回表 / 覆盖索引最左前缀

  • B+ 树 vs B 树：B 树数据分散在各层，B+ 树数据只在叶子层且链表相连 → 范围查询更优、IO 更稳定。
  • 回表：二级索引查到主键后再走主键树取行；若索引已含所需列则为覆盖索引，免回表。

布隆过滤器 · Bloom Filter

缓存穿透防护 / 爬虫 URL 去重
插入/查询 O(k) ▼

核心思想

一个很长的位数组 + k 个独立哈希函数。插入时把 key 经 k 个哈希映射到的位全置 1；查询时若 k 个位全为 1 则「可能存在」，只要有一位为 0 则「一定不存在」。它用极小空间判断「不存在」，代价是有极小误判率（假阳性），且不支持删除（除非用 Counting Bloom）。

时间复杂度

  • 插入 / 查询：O(k)（k 为哈希函数个数，常数）
  • 空间：O(m)，与元素数量无关，远小于 Hash Set

实际系统中的应用

缓存穿透防护爬虫 URL 去重HBase / Cassandra 块过滤垃圾邮件黑名单

  • 缓存穿透防护：恶意请求查询不存在的 key 会击穿到数据库。在缓存前加布隆过滤器，不存在的 key 直接拒绝，保护 DB。
  • 爬虫 URL 去重：已抓取的 URL 放入过滤器，避免重复抓取，内存占用极低。

👉 交互演示：布隆过滤器

向 16 位数组写入字符串（3 个哈希函数），再检测某 key 是否存在

面试考点

误判率与 m/k 关系不支持删除与 Hash Set 对比

  • 位数组越大、哈希函数越合适 → 误判率越低；误判率 ≈ (1 - e^(-kn/m))^k。
  • 「能证明不存在，不能证明存在」是它最关键的语义，记住：假阳性可能存在，假阴性绝不发生。

一致性哈希 · Consistent Hashing

分布式缓存分片 / 负载均衡
定位 O(log n) ▼

核心思想

把「节点」和「数据 key」都哈希到一个 2^32 的环形空间（hash ring）。数据顺时针找到的第一个节点即为其归属。当节点增减时，只有环上相邻的一小段数据需要迁移，而非全部重分布——解决了普通取模哈希在扩缩容时几乎全量 rehash 的痛点。

为缓解数据倾斜，引入虚拟节点（vnode）：每个物理节点映射出多个虚拟点均匀散布在环上，让负载更均衡。

时间复杂度

  • 定位目标节点：O(log n)（n 为环上虚拟节点数，可用有序结构二分查找）
  • 节点增减的数据迁移量：O(1/n)，仅影响相邻区间

实际系统中的应用

Redis Cluster 槽分配Memcached 客户端分片一致性哈希负载均衡DynamoDB / Cassandra 数据分片

  • 分布式缓存：节点宕机或扩容时，只有落到失效节点上的key需迁移，其余客户端路由不变，系统抖动最小。
  • Redis Cluster：用 16384 个哈希槽（类似一致性哈希的离散化）在节点间分配。

面试考点

节点增减的迁移量数据倾斜与虚拟节点与普通取模对比

  • 普通 hash(key) % N：N 变化时几乎全量重映射；一致性哈希仅影响 1/N 的数据。
  • 虚拟节点数越多，负载越均衡，但内存与计算开销略增。
