DRY — 不要重复自己
Don't Repeat Yourself

每一条知识/逻辑只应有一个单一、明确的表示形式。重复是维护成本的根源。

点击展开详情 →

一句话解释

系统中每一段知识或逻辑必须只有一个单一的、权威的表现形式。

代码反例 / 正例

❌ 反例：重复代码
function calcArea(r) { return Math.PI*r*r; }
function calcCircum(r) { return 2*Math.PI*r; }
// 如果 π 值变化，需要改两处
✅ 正例：提取常量
const PI = Math.PI;
function calcArea(r) { return PI*r*r; }
function calcCircum(r) { return 2*PI*r; }
// π 只在一处定义

生活化类比

📋 餐厅菜单：每种菜品的配方只写在厨师手册一处，所有厨师共用。如果改配方，只改一处而不是每个厨师各抄一份。

面试考点

❓ 如何判断代码中是否存在"重复"？
💡 不仅是代码行复制，还包括逻辑重复（不同函数实现相同业务规则）。DRY 的核心是"知识单一来源"，而非简单的代码行去重。

YAGNI — 不要过度设计
You Aren't Gonna Need It

不要编写当前不需要的功能。预测未来需求往往是浪费时间且引入复杂度。

点击展开详情 →

一句话解释

不要编写当前不需要的功能——你"不会需要它"的概率远大于你需要它的概率。

代码反例 / 正例

❌ 反例：过度设计
// 只需支持JSON，却预想了XML/YAML/Protobuf
class DataParser {
  parseJSON() {}
  parseXML() {}
  parseYAML() {}
  parseProtobuf() {}
}
// 实际需求只有JSON，却增加了大量维护负担
✅ 正例：按需扩展
class JSONParser {
  parse(data) { return JSON.parse(data); }
}
// 需要其他格式时再扩展（开闭原则）

生活化类比

🏠 买房：你不会因为"可能将来会生子"就买五居室。按需购买、逐步升级，才是明智的消费观。

面试考点

❓ YAGNI 和"预见性设计"矛盾吗？
💡 不矛盾。YAGNI 反对的是"为不确定的未来付出确定的现在成本"。架构弹性（通过抽象和接口实现）与 YAGNI 并不冲突——关键在于抽象的成本是否值得。
✨
KISS — 保持简单
Keep It Simple, Stupid

系统设计应尽可能简单。复杂是Bug的温床，简单是可靠的基础。

点击展开详情 →

一句话解释

设计应保持尽可能的简单，避免不必要的复杂性——简单性是可靠性的基石。

代码反例 / 正例

❌ 反例：过度抽象
// 用3层抽象做简单的字符串拼接
class StringContext {}
class StringStrategyFactory {}
class StringProcessorContext {}
const result = processor.process(str);
// 简单任务用复杂方案
✅ 正例：直接明了
const result = str1 + str2;
// 需要拼接？直接 + 号
// 90% 场景这就够了

生活化类比

🔧 瑞士军刀 vs 工具箱：出门只需一把瑞士军刀就能解决大部分问题，带齐整个工具箱反而增加负担。

面试考点

❓ KISS 与"可扩展性"冲突吗？
💡 真正的简单不是没有扩展能力，而是扩展方式简单。好的简单设计是"通过简单机制支持可能的扩展"，而非"为了扩展而预先复杂化"。
🧩
分离关注点
Separation of Concerns

将系统划分为不同功能模块，每个模块只负责一个关注点。单一职责、模块化。

点击展开详情 →

一句话解释

每个模块/类/函数应该只有一个引起它变化的原因——即只负责一个关注点。

代码反例 / 正例

❌ 反例：混杂职责
class UserService {
  validate(data) {}
  saveToDB(data) {}
  sendEmail(data) {}
  generateReport(data) {}
}
// 一个类负责验证、存储、邮件、报表
✅ 正例：各司其职
class UserValidator { validate(data) {} }
class UserRepository { save(data) {} }
class EmailService { send(data) {} }
class ReportGenerator { generate(data) {} }
// 每个类一个职责

生活化类比

🏢 公司运营：财务部管钱、产品部管需求、技术部管开发。各部门专注本职，通过流程协作。如果财务部也做产品，产品部也写代码，公司必定混乱。

面试考点

❓ 如何判断一个类是否"职责单一"？
💡 使用"为什么测试"原则：如果修改类的原因超过一个，说明它有多个职责。单一职责的类应该能用一个"因为...所以修改了它"的句式解释清楚。
