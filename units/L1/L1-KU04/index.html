DRY

通用
Don't Repeat Yourself · 不要重复自己
每一段知识/逻辑在系统中都应有单一、权威的表示。
点击展开 ▾

核心思想

同样的代码不应出现两次。同样的业务逻辑不应散布在多处。重复是维护的敌人 —— 改一个漏一个。

反例（Bad）

// 多处复制同样的验证逻辑
function validateUserA() { /* 20行验证 */ }
function validateUserB() { /* 完全相同的20行 */ }

正例（Good）

// 提取为单一函数，复用
function validateUser(user) { /* 唯一一份验证 */ }

面试考点

"DRY 不只是代码复用，更是知识的复用。一个需求变更时，应该只需要改一个地方。"

YAGNI

通用
You Aren't Gonna Need It · 不要过度设计
不要为"可能"需要的功能付出"确定"的开发成本。
点击展开 ▾

核心思想

不要实现当前不需要的功能。不要预留"以后可能会用到"的抽象层。今天的过度设计，就是明天的技术债。

反例（Bad）

// 一开始就搞了 10 种格式解析器，实际只用 JSON
interface Parser { ... }
class JsonParser, XmlParser, YamlParser, ProtobufParser...

正例（Good）

// 先做 JSON，未来真要扩展再加
function parse(data) { return JSON.parse(data); }

面试考点

"YAGNI 不是不设计，而是不为未经验证的假设买单。先让它跑起来，再让它跑得好。"

KISS

通用
Keep It Simple, Stupid · 保持简单
简单性是可靠性的基石。避免不必要的复杂性。
点击展开 ▾

核心思想

代码应该像在读一个故事，而不是在解一道谜题。任何人都能快速理解的方案，就是好方案。

反例（Bad）

// 为了炫技写成一行
const r=a.map(b=>b.c.filter(d=>d.e>0).reduce((p,q)=>p+q.f,0));

正例（Good）

const validItems = items.filter(item => item.score > 0);
const total = validItems.reduce((sum, item) => sum + item.price, 0);

面试考点

"简单 ≠ 不抽象，而是刚好够用的抽象。能被人读懂的代码，才能被正确维护。"

分离关注点

通用
Separation of Concerns · 单一职责
每个模块/类只有一个引起它变化的原因。
点击展开 ▾

核心思想

把一件事的不同方面分开。前端展示、后端逻辑、数据存储、错误处理 —— 每个关注点各司其职。

反例（Bad）

// 一个类做了所有事
class User {
  saveToDB(); renderHTML(); sendEmail(); validateInput();
}

正例（Good）

class UserService { validate(){} save(){} }
class UserView { render(){} }
class UserNotifier { sendWelcomeEmail(){} }

面试考点

"一个类只有一个职责。如果一个类有多个修改理由，就拆。高内聚、低耦合。"
